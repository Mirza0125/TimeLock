## Phase Goal

ROADMAP Goal (verbatim): A reproducible Expo SDK 57 project runs on the emulator with full quality tooling, the shared enforcement contract is frozen, and the API 36 block-launch question is answered with a working fallback before any enforcement code depends on it.

This plan's slice: **the frozen enforcement contract (FND-05).** A developer (and the Phase 2/4 evaluators) gets one typed ScreenGuard contract plus a shared, validated set of rule-evaluation vectors that encode spec §6.3 before any evaluator exists.

<objective>
Freeze the ScreenGuard TypeScript contract (spec §12.2 interface and §16.1 domain types, plus the evaluation input/output that the vectors need). Author 21 shared JSON rule-evaluation vectors, one or more per §6.3 evaluation step, and load and validate them in Jest. The Kotlin/JUnit loader for the same file is Plan 01-06.

Purpose: The Kotlin LimitEngine and the TS reference evaluator (Phases 2/4, ENF-05) must agree on every vector. Writing the contract and vectors first means both evaluators are built against the same specification instead of drifting apart.
Output: ScreenGuard.types.ts, ruleEvaluationVectors.ts (types + runtime parser, no evaluator), rule-evaluation.json, 2 Jest test files.
</objective>

## Flagged Assumptions (from the spec-less edge/prohibition probe, FND-05)

These are recorded here instead of being encoded silently. Phase 2/4 must confirm or revise them with the user:
1. **Open-count semantics.** `usageToday.opens` includes the current open, and the rule blocks when opens > maxOpens. This follows "Opening beyond max → blocked" and ROADMAP P4 SC3 "after the Nth open". Encoded in two vectors.
2. **Grant expiry boundary.** A grant is active while nowMs < until, so at exactly `until` it has expired. Encoded in one vector.
3. **NOT encoded (ambiguous — open questions for Phases 2 and 4):**
   - (a) When a schedule and a daily limit both block with different `until` values, which reason and `until` the block screen reports ("most restrictive" versus the ordered steps). Only the case where both readings agree is encoded.
   - (b) How usage of a category-based group is summed (it depends on installed-app categories).
   - (c) Whether a grant can override a schedule in self mode. Step 6 lists only reasons 3–5; the parenthetical mentions child mode.
