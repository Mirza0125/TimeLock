## Phase Goal

ROADMAP Goal (verbatim): A reproducible Expo SDK 57 project runs on the emulator with full quality tooling, the shared enforcement contract is frozen, and the API 36 block-launch question is answered with a working fallback before any enforcement code depends on it.

This plan's slice: **the answer.** The developer runs one command that exercises both block paths on API 36 and gets a written, evidence-backed decision about which path is primary, before Phase 2's enforcement depends on it.

<objective>
Build a repeatable spike runner that exercises the activity-first cascade and the forced fallback N=5 times each on the API 36 emulator, with controls for known background-launch exemptions. It captures logcat, StrictMode and screenshot evidence into the phase directory and emits summary.json. Then apply a pre-declared decision rule, record the primary path in an ADR-style decision doc, and align the production default strategy with it.

Purpose: FND-03 and ROADMAP criterion 3 require both paths to be exercised and the primary path recorded as a decision. STATE.md lists this as the gating blocker for every enforcement phase. A fallback-only result is a valid, planned outcome.
Output: scripts/spike-block-launch.sh, spike-evidence/*, docs/decisions/0001-block-launch-path.md, the DEFAULT_STRATEGY alignment, and PROJECT/STATE/SKELETON updates.
</objective>

Exemptions the runner must control for, so that the activity path is not credited for a launch that some other exemption allowed:
- The app having a visible window, or an activity started or finished very recently. Mitigation: wait at least 12 s after ScreenLimiter was last visible before every trial.
- A granted overlay permission. Mitigation: the APK does not declare it (Plan 01-05 audit); the runner re-checks `dumpsys package` and `appops`.
- A notification tap is an exempt PendingIntent start by design. That is why it is the fallback's re-entry point, and it is not counted as activity-path evidence.
